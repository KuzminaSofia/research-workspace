### 1. Workspace Overview

**Основная функция:**  
Центральная точка Workspace — показывает состояние исследования и даёт вход во все остальные экраны.

**Ключевые элементы:**

- название и описание Workspace;
- список Research Tasks со статусом каждой;
- кнопка **Create Research Task**;
- список Decisions;
- секция **Ask Workspace** (follow-up question area встроена сюда же, см. экран 6);
- переходы к Task / Decision.

**Связь с user journey:**  
Точка входа для шага 2 (Define Research Question) и точка возврата после шага 9 (Review/Accept Decision).

---
### 2. Research Task Page

**Основная функция:**  
Единое рабочее место для одной research task — покрывает всю цепочку `Sources → Run → Evidence → Claims → Decision` без отдельных экранов под каждый шаг.

**Ключевые элементы:**

- title и research question;
- статус task;
- секция **Sources** + кнопка **Add Source**;
- кнопка **Run Research**;
- блок статуса **Research Run** (Queued / Running / Review Required / Completed / Failed / Cancelled — по `ResearchRun.status`);
- секция **Evidence** (карточки, переход в source/evidence panel);
- секция **Claims** (карточки, переход в claim review panel);
- **Summary** + кнопка **Create Decision**.

**Связь с user journey:**  
Покрывает шаги 3–7 (Add/Find Sources → Run Research → Review Evidence → Validate Claims → Create Decision) как секции одной страницы, не отдельные экраны.

---

### 3. Source / Evidence Panel

**Основная функция:**  
Проверить, что конкретный evidence item действительно подтверждён источником.

**Ключевые элементы:**

- Source: title, url, published date, содержимое/превью;
- Evidence Item: excerpt, location, note, confidence (все поля из `EvidenceItem` отображаются в самой карточке Evidence Item, не в превью источника);
- ссылка на оригинальный источник;
- действия **Approve / Reject / Edit**;
- связь Evidence → Claim (какой claim это подтверждает).

**Связь с user journey:**  
Шаг 5 — Review Evidence.

---

### 4. Claim Review Panel

**Основная функция:**  
Проверить draft claim и назначить ему финальный статус.

**Ключевые элементы:**

- текст Claim, текущий статус, confidence;
- Supporting Evidence (связанные evidence items);
- **Set status**: Supported / Weak / Conflicting / Outdated (плюс возврат в Draft — один контрол, не два);
- review note;
- reviewer.

**Доменное правило, которое должно быть видно в UI:**  
`supported` невозможен без evidence; AI-generated claim стартует как `draft`.

**Связь с user journey:**  
Шаг 6 — Validate Claims.

---

### 5. Decision Page

**Основная функция:**  
Сформулировать decision на основе проверенных claims, показать его итоговый брифинг и провести финальный review/accept — **Decision Brief встроен в этот же экран**, отдельного screen под него в рамках F2 нет.

**Ключевые элементы:**

- Decision title, Decision text, Rationale;
- Linked Claims (со статусами — видно, какие Supported/Weak);
- **Decision Brief поля**: Confidence, Open Questions (Key Claims и Supporting Evidence уже видны через Linked Claims).
  **Open question:** в текущей `04-domain-model.md` у `Decision` нет собственного поля `confidence` — оно есть только у `Claim` и у `EvidenceItem`. На макете `Decision confidence` показан как отдельное значение в Decision Brief; пока не уточнено, откуда оно берётся (агрегируется из confidence связанных claims, приходит отдельно из `ArtifactManifest`/agent output, или это просто предположение для wireframe без готового источника данных). До уточнения backend/API контракта это поле на фронте остаётся идеей представления, а не зафиксированным контрактом.
- статус Decision (Proposed / Accepted / Rejected / Needs Review);
- reviewer / decided_by;
- действия **Accept / Send to Review / Reject**.
  **Open question:** семантика **Send to Review** не определена текущим контрактом. В `04-domain-model.md` у `Decision.status` есть значения `proposed`, `accepted`, `rejected`, `superseded`, `needs_review` — отдельного состояния вроде `in_review` нет, а на макете Decision уже показан в статусе `Proposed`. Непонятно, что именно должен делать backend после нажатия кнопки: менять `Decision.status` (и на какое значение — `needs_review`?), назначать/уведомлять reviewer без смены статуса, или `Proposed` уже сам по себе означает "ожидает review" и кнопка вообще не меняет status, а выполняет другое действие (например, отправку уведомления). До определения review workflow на backend это остаётся open question, а не зафиксированным поведением.
- пояснение правила: Accept недоступен, пока связанные claims не прошли review, либо доступен через явный human override (домен: `04-domain-model.md`, "Decision может стать `accepted` только с reviewed claims или с явным human override").
  **Open question:** точный критерий "reviewed claims" для Accept — достаточно ли хотя бы одного non-draft claim среди Linked Claims, или требуется, чтобы review прошли все Linked Claims — в domain model явно не зафиксирован. Критерий нужно зафиксировать в domain/API контракте.

**Связь с user journey:**  
Покрывает шаги 7–9 разом: Create Decision → Generate Decision Brief → Review/Accept Decision.

### 6. Follow-up Question Area

**Основная функция:**  
Задать вопрос по накопленной памяти Workspace и, если её недостаточно, создать follow-up research task.

**Ключевые элементы:**

- поле вопроса + кнопка **Ask**;
- **Workspace Answer**: текстовый ответ + ссылки View Evidence / View Claims / View Sources;
- счётчики Sources / Claims / Decisions;
- индикатор **Memory sufficient?**;
- кнопка **Create Follow-up Task** (переиспользует flow Create Research Task, отдельного экрана под это не создаём).

**Связь с user journey:**  
Шаг 10 — Ask Workspace / Follow-up Question.
