## 1. Обзор проекта

**AI Research & Decision Workspace** — продукт, который помогает команде превращать исследование в проверяемую, переиспользуемую и обновляемую память.

Главная цепочка продукта:

```text
research question → sources → evidence → claims → decisions → updates
```

Ценность продукта заключается не в создании обычного LLM-чата или длинного research report, а в сохранении проверяемой истории исследования: какие вопросы изучались, какие источники использовались, какие evidence лежали под выводами, какие claims были подтверждены или ослаблены и почему было принято конкретное решение.

MVP должен позволять пройти полный цикл:

```text
создать workspace
→ создать research task
→ добавить / найти / импортировать sources
→ запустить контролируемое исследование
→ получить структурированные артефакты
→ проверить evidence и draft claims
→ создать decision
→ задать follow-up вопрос по памяти workspace
→ при необходимости создать follow-up research task
```

Продуктовый принцип:

> Agent помогает найти и структурировать информацию. Только проверенные человеком evidence, claims и decisions становятся знанием команды.

Источник: `01-product-vision.md`.

# F1. Понять MVP Flow

## 2. User Journey

Пользователь проходит следующий путь:

| Шаг | Этап | Действие пользователя | Результат |
|---|---|---|---|
| 1 | Create Workspace | Создает workspace, задает название и описание исследовательской области | Создан контейнер исследования |
| 2 | Define Research Question | Создает Research Task и формулирует исследовательский вопрос | Появляется конкретная задача исследования |
| 3 | Add / Find Sources | Добавляет URL, PDF, Doc, GitHub, видео или manual note | Формируется набор источников |
| 4 | Run Research | Запускает контролируемый Research Run | Agent структурирует информацию |
| 5 | Review Evidence | Проверяет конкретные Evidence Items | Непроверенные фрагменты становятся проверенными |
| 6 | Validate Claims | Проверяет Claims и назначает статус | Формируются подтвержденные / слабые / конфликтующие / устаревшие claims |
| 7 | Create Decision | Формулирует решение на основе проверенных claims | Создается Decision |
| 8 | Generate Decision Brief | Система собирает краткий итог исследования | Decision, Rationale, Key Claims, Supporting Evidence, Confidence, Open Questions |
| 9 | Review / Accept Decision | Проверяет и принимает либо отправляет решение на повторный review | Decision становится принятым или остается на review |
| 10 | Ask Workspace | Задает вопрос по накопленной памяти | Ответ по Sources / Evidence / Claims / Decisions или предложение нового Follow-up Task |

Основной flow из `user-journey.md`:

```text
Create Workspace
↓
Define Research Question
↓
Add / Find Sources
↓
Run Research
↓
Review Evidence
↓
Validate Claims
↓
Create Decision
↓
Generate Decision Brief
↓
Review / Accept Decision
↓
Ask Workspace / Follow-up Question
```

## 3. Screens, необходимые для MVP

Для F2 были определены шесть основных экранов:

1. **Workspace Overview**
2. **Research Task Page**
3. **Source / Evidence Panel**
4. **Claim Review Panel**
5. **Decision Page**
6. **Follow-up Question Area**

Важные архитектурные решения по экранной структуре:

- Research Task Page объединяет цепочку `Sources → Run → Evidence → Claims → Decision`.
- Decision Brief не вынесен в отдельный экран, а встроен в **Decision Page**.
- Follow-up Question Area встроен в **Workspace Overview**, а не является отдельным route.

Это соответствует описанию экранов MVP и макетам Figma.

- список Research Tasks и их статусы;
- **Create Research Task**;
- список Decisions;
- **Ask Workspace**;

- Research Task `Market analysis` со статусом `Review`;
- Research Task `Technology evaluation` со статусом `Completed`;
- Decision со статусом `Accepted`;
- встроенную область Ask Workspace.

```text
→ Run Research
→ Review Evidence
→ Validate Claims

```

В Figma success/review вариант показывает `Review Required` для Research Run и `Draft` для AI-generated Claim.

Шаг **Review Evidence**.

### Основные элементы

- статус;

## 8. Decision Page

### Назначение

Сформулировать Decision на основе проверенных claims, показать итоговый Decision Brief и провести финальный review.

### Основные элементы

- Decision title;
- Decision text;
- Rationale;
- Linked Claims;
- Confidence;
- Open Questions;
- Decision status;
- reviewer / decided_by;
- **Accept**;
- **Send to Review**;
- **Reject**.

Open questions:
- **Confidence** как отдельное поле Decision Brief не имеет соответствия в `04-domain-model.md` — у `Decision` нет собственного `confidence`, оно есть только у `Claim`/`EvidenceItem`. Источник значения (агрегация из claims, отдельное поле artifact/agent output, либо пока не определено) требует уточнения backend/API контракта.
- **Send to Review** — семантика transition не определена: в domain model у `Decision.status` нет состояния `in_review`, а на макете Decision уже показан как `Proposed`. Непонятно, меняет ли действие `Decision.status`, назначает reviewer без смены статуса, или `Proposed` уже само по себе означает "ожидает review". Уточняется отдельно, до определения review workflow на backend.

### Decision Brief

В рамках MVP он встроен в этот экран и включает:

- Decision;
- Rationale;
- Key Claims;
- Supporting Evidence;
- Confidence (open question — источник поля в domain model не определён, см. раздел выше в этом документе);
- Open Questions.

Key Claims и Supporting Evidence представлены через Linked Claims и связанные evidence.

### Доменное правило

Accepted decision требует reviewed claims, если не применен явный human override.

Open question: точный критерий "reviewed claims" (хотя бы один non-draft claim среди Linked Claims, или все Linked Claims не в draft) в domain model явно не зафиксирован — уточняется в backend/API контракте.

---

## 9. Follow-up Question Area

### Назначение

Позволяет задавать вопросы по накопленной памяти Workspace и определять, достаточно ли существующих данных для ответа.

### Основные элементы

- поле вопроса;
- **Ask**;
- Workspace Answer;
- View Evidence;
- View Claims;
- View Sources;
- счетчики Sources / Claims / Decisions;
- индикатор **Memory sufficient?**;
- **Create Follow-up Task**.

### Поведение при недостаточной памяти

Если текущей памяти недостаточно, система не должна выдавать неполный ответ за окончательное знание. Вместо этого пользователь получает предложение создать Follow-up Research Task.

Follow-up Task использует уже существующий flow создания Research Task.

# F3. UI State Map

## 10. Workspace Overview

### Empty

Workspace создан, но Research Tasks и Decisions отсутствуют. Показывается placeholder и предложение **Create Research Task**.

### Loading

Research Tasks и Decisions еще загружаются — используются skeleton placeholders.

### Error

Не удалось получить данные Workspace. Показывается ошибка и **Retry**.

### Success

Списки Research Tasks и Decisions заполнены.

### Draft / Review

Research Task со статусом `review` получает соответствующий бейдж и требует внимания пользователя.

---

## 11. Research Task Page

### Empty

Sources отсутствуют. Поведение **Run Research** зависит от `ResearchRun.mode`: для `manual_sources` (единственный режим в MVP) кнопка заблокирована или сопровождается подсказкой добавить хотя бы один source; для `search_assisted` отсутствие source потенциально нормально (source может появиться из самого workflow) — это open question, не входящий в MVP-скоуп F1–F4, и не зафиксирован здесь как domain rule.

### Loading

`ResearchRun.status = queued` или `running`.

Evidence и Claims показывают состояние ожидания завершения run.

### Error

`ResearchRun.status = failed`.

Показываются:

- Failed;
- `error_message`;
- **Retry Run**.

Для `cancelled` используется отдельное по смыслу состояние с **Re-run** без сообщения об ошибке.

### Success

`ResearchRun.status = completed`, Evidence и Claims заполнены, доступен **Create Decision**.

### Draft / Review

`ResearchRun.status = review_required`.

Результаты исследования были получены агентом, но требуют human review.

---

## 12. Source / Evidence Panel

### Empty

Для выбранного Source отсутствуют Evidence Items.

### Loading

Загружается исходное содержимое или Evidence Item — показываются skeleton placeholders.

### Error

Source недоступен или `raw_content_ref` не может быть загружен. Пользователь может перейти к **Open original source**.

### Success

Отображаются Source, Evidence Item, excerpt, location, note, confidence и действия Approve / Reject / Edit.

### Draft / Review

Evidence извлечен агентом, но еще не подтвержден человеком — UX это отражает через доступность действий Approve/Reject/Edit. Open contract question: в domain model у `EvidenceItem` нет явного review-состояния (аналога `Claim.status`) и нет audit-полей `reviewed_by` / `reviewed_at` — состояние и поля для сохранения результата review предстоит зафиксировать в backend/API контракте.

---

## 13. Claim Review Panel

### Empty

Supporting Evidence отсутствует.

Правило:

```text
Supported недоступен без связанного evidence.
```

### Loading

Загружается Claim и связанные Evidence Items.

### Error

Не удалось сохранить новый статус. Пользователь получает сообщение об ошибке, а статус возвращается к предыдущему значению.

### Success

Claim имеет supporting evidence, сохраненный review note и reviewer.

### Draft / Review

`Claim.status = draft`.

Это стартовое состояние AI-generated Claim.

---

## 14. Decision Page

### Empty

Decision только создан, но Linked Claims еще нет. Acceptance недоступен.

### Loading

Выполняется Accept / Send to Review / Reject — выбранное действие показывает loading state.

### Error

Не удалось изменить Decision status. Статус остается прежним, например `Proposed`, и действие можно повторить.

### Success

Decision имеет:

- Proposed;
- Linked Claims;
- Confidence;
- Open Questions.

### Draft / Review

Decision находится в `needs_review` или содержит непроверенные claims.

Accept недоступен, пока не выполнено доменное условие о reviewed claims, кроме explicit human override. Open question: точный критерий "reviewed claims" (хотя бы один non-draft claim vs все Linked Claims не в draft) не зафиксирован в domain model.

# F4. Evidence-First Claim Card

## 16. Цель компонента

Claim Card должен позволять reviewer быстро ответить на вопрос:

> Что утверждается, насколько это уверенно и на каком evidence это основано?

Компонент строится вокруг evidence-first подхода: claim не рассматривается как самостоятельное знание без связи с конкретными фрагментами источников.

## 17. Состав Claim Card

### Claim text

Основное проверяемое утверждение.

Пример:

> Approach X reduces implementation complexity compared with approach Y.

### Status

Показывает текущий уровень валидации:

```text
Draft
Supported
Weak
Conflicting
Outdated
```

### Confidence

Например:

```text
Confidence 0.78
```

### Linked Evidence

Для каждого связанного Evidence отображаются:

- excerpt;
- источник;
- confidence evidence;
- переход к source.

### Source title

Например:

```text
Official documentation
```

### Review actions

```text
Supported
Weak
Conflicting
Outdated
Draft
```

В интерфейсе также предусмотрено **Open full review** для перехода в Claim Review Panel.

# 19. Связь F1–F4 с доменной моделью

| Требование | UI / решение | Доменная основа |
|---|---|---|
| Research Task должен иметь статус | Workspace Overview / Research Task Page | `ResearchTask.status` |
| Research Run должен отражать процесс | Research Task Page | `ResearchRun.status` |
| Ошибка research run должна быть видна | Research Task Page / Error State | `ResearchRun.error_message` |
| Evidence должен быть проверяемым | Source / Evidence Panel | `EvidenceItem` |
| Claim должен иметь статус | Claim Review Panel / Claim Card | `Claim.status` |
| Claim должен быть связан с Evidence | Claim Card / Supporting Evidence | many-to-many Claim ↔ Evidence |
| Supported невозможен без evidence | Claim Review Panel / Empty State | domain rule |
| AI claim начинается как Draft | Claim Card / Draft State | domain rule |
| Decision строится на claims | Decision Page | many-to-many Decision ↔ Claim |
| Accepted Decision требует review | Decision Page / Review State | domain rule |
| Follow-up использует память Workspace | Ask Workspace | Sources / Claims / Decisions |

# 20. Архитектурная основа решения

Backend описан как прагматичная Clean / Hexagonal Architecture.

## Domain

Основные сущности:

```text
Workspace
ResearchTask
Source
EvidenceItem
Claim
Decision
ResearchRun
ArtifactManifest
Update
```

## Application

Основные use cases:

```text
Create Workspace
Create Research Task
Add Source
Start Research Run
Review Claim
Create Decision
Ask Workspace
Export Decision Brief
```

Application зависит от ports, а не от конкретной infrastructure.

## Infrastructure

Отвечает за реализации repositories, storage, LLM adapter, search, queue и migrations.

## API

HTTP-слой остается тонким:

```text
request/response schemas
→ validation
→ use case
→ response mapping
```

Бизнес-логика не должна находиться внутри API.

## Agent Service Boundary

Agent service работает как отдельный runtime-компонент и выполняет research pipeline:

```text
ingest sources
→ extract evidence
→ create draft claims
→ link claims to evidence
→ generate decision brief
→ save artifacts
→ send result to human review
```

Главный принцип: результат agent остается `draft` до human review.

---

# 21. Основные доменные правила

1. `Claim` без evidence не может стать `supported`.
2. AI-generated Claim стартует в состоянии `draft`.
3. Accepted Decision требует reviewed claims, кроме explicit human override.
4. Outdated Claim должен подсвечивать связанные Decisions как candidates for review.
5. Результат `ResearchRun` не становится accepted knowledge автоматически.

Эти правила непосредственно отражены в UI State Map и макетах Figma.
