# AI Research & Decision Workspace

Краткое описание проекта

## 1. Идея проекта

AI Research & Decision Workspace - это внутренняя рабочая среда для команды, которая помогает не просто проводить исследования с помощью AI, а сохранять их в виде проверяемой памяти:

```text
research question -> sources -> evidence -> claims -> decisions -> updates
```

Главная идея: команда не должна каждый раз начинать исследование заново. Если месяц назад уже изучали тему, система должна показать:

- что команда уже выяснила;
- на каких источниках это основано;
- какие выводы были сделаны;
- какие решения были приняты;
- что могло устареть и требует перепроверки.

Это не продукт "еще один исследовательский агент". Продукт хранит исследовательскую память команды и связывает исследования с реальными решениями.

## 2. Бизнес-проблема

В технологических, аналитических и R&D-командах постоянно появляются вопросы:

- какие подходы сейчас используют для evaluation LLM-агентов;
- стоит ли внедрять GraphRAG;
- какие модели подходят для OCR технической документации;
- какие open-source решения можно взять за основу;
- какие ограничения и риски есть у выбранного подхода.

Обычно процесс выглядит так:

```text
появился вопрос
-> кто-то ищет статьи, посты, репозитории, документацию
-> делает выводы
-> пишет сообщение или документ
-> команда принимает решение
-> через 2 месяца похожий вопрос возникает снова
-> все ищут почти заново
```

Проблема не только в поиске. Проблема в том, что результат исследования плохо сохраняется как командное знание.

Типичные потери:

- выводы остаются в чатах и личных заметках;
- непонятно, на какие источники опиралось решение;
- сложно понять, какие выводы устарели;
- новые участники команды не видят историю рассуждений;
- похожие исследования повторяются несколько раз;
- решения принимаются без прозрачной связи с evidence.

## 3. Что ускоряет продукт

Продукт ускоряет не один поисковый запрос, а полный цикл работы с исследовательской информацией.

Он помогает быстрее:

- запускать research-задачи по повторяющимся темам;
- собирать источники и кратко фиксировать их ценность;
- выделять claims - проверяемые утверждения из исследования;
- связывать claims с evidence - источниками, цитатами, документами, метаданными;
- принимать решения на основании уже собранных данных;
- возвращаться к старым решениям и понимать, почему они были приняты;
- находить устаревшие выводы и запускать повторную проверку.

## 4. Основные сущности

В проекте важно думать не только про чат с AI. Основная ценность находится в структуре данных.

### Workspace

Рабочее пространство команды или проекта. Например:

- "LLM Agent Observability";
- "OCR for Technical Documents";
- "Internal RAG Platform".

### Research Task

Исследовательская задача. Например:

> "Сравнить подходы к evaluation LLM-агентов в production".

### Source

Источник информации:

- статья;
- документация;
- GitHub-репозиторий;
- PDF;
- внутренний документ;
- пост;
- видео;
- issue или discussion.

### Evidence

Конкретный фрагмент источника, на который можно сослаться:

- цитата;
- абзац;
- таблица;
- benchmark;
- changelog;
- фрагмент документации.

### Claim

Проверяемое утверждение, извлеченное из исследования.

Пример:

> "Для оценки LLM-агентов недостаточно только golden dataset; нужны трассы tool calls и анализ failure modes".

Claim должен иметь связь с evidence. Если утверждение не связано с источниками, оно должно быть помечено как неподтвержденное или требующее проверки.

### Decision

Решение команды.

Пример:

> "В MVP observability используем trace-based evaluation, а human feedback оставляем на второй этап".

Decision должен ссылаться на claims и evidence, которые повлияли на решение.

### Update

Событие, которое меняет контекст:

- появился новый источник;
- старый источник обновился;
- изменилась документация API;
- вышла новая версия библиотеки;
- старый claim стал сомнительным.

## 5. Пример пользовательского сценария

Команда думает, как построить observability для LLM-агентов.

1. Тимлид создает workspace "LLM Agent Observability".
2. Создает research task: "Какие подходы использовать для evaluation LLM-агентов в production?"
3. AI-модуль помогает собрать источники: статьи, документацию LangSmith, OpenTelemetry, blog posts, GitHub-проекты.
4. Система сохраняет sources и выделяет evidence.
5. Из evidence формируются claims:
   - "Оценивать нужно не только final answer, но и траекторию действий агента".
   - "Для production важно хранить traces и tool call metadata".
   - "Offline evals не заменяют runtime monitoring".
6. Команда обсуждает claims и принимает decision:
   - "В первом релизе храним traces, tool calls, input/output и user feedback".
7. Через месяц выходит новая версия используемой библиотеки.
8. Система помечает связанные claims как требующие перепроверки.
9. Новый стажер открывает workspace и видит не только итоговое решение, но и путь к нему: sources -> evidence -> claims -> decision.

## 6. MVP

MVP должен доказать, что продукт умеет превращать research в структурированную память, а не просто генерировать отчеты.

Минимальный scope:

- создание workspace;
- создание research task;
- добавление источников вручную или через простой search/import;
- сохранение краткого summary по каждому source;
- выделение claims из research task;
- связь claim с одним или несколькими sources/evidence;
- создание decision на основе claims;
- просмотр страницы workspace: активные research tasks, claims, decisions;
- простой статус claim: `draft`, `supported`, `weak`, `outdated`;
- экспорт research summary в Markdown.

Необязательное для первого MVP:

- полноценный автономный Deep Research agent;
- сложный knowledge graph;
- real-time collaborative editing;
- enterprise permissions;
- интеграции с Jira/Confluence/Slack;
- автоматический мониторинг обновлений источников.

## 7. Роли участников

### Backend

Фокус:

- модель данных;
- API для workspace, research tasks, sources, claims, decisions;
- хранение связей между сущностями;
- статусы claims;
- импорт источников;
- очередь фоновых задач для AI-обработки.

Примеры задач:

- спроектировать таблицы `workspaces`, `research_tasks`, `sources`, `evidence_items`, `claims`, `decisions`;
- сделать REST или tRPC API для CRUD-операций;
- реализовать endpoint "extract claims from source summary";
- добавить историю изменения claim status.

### Fullstack

Фокус:

- удобный интерфейс для работы с research memory;
- страницы workspace, research task, source, decision;
- flow "из источников в claims, из claims в decision";
- отображение evidence рядом с утверждениями;
- состояния loading/error/empty.

Примеры задач:

- сделать страницу workspace overview;
- сделать экран research task с колонками Sources / Claims / Decisions;
- сделать карточку claim с привязанными evidence;
- сделать форму создания decision;
- сделать экспорт в Markdown.
